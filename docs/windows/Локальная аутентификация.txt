Локальная аутентификация в Windows: что происходит после ввода пароля.
Локльная аутентификация - процесс проверки подлинности пользователя, при котором учётные данные проверяются непосредственно на устройстве или в системе, без отправки их на внешний сервер. Проще говоря, это то, что происходит, когда вы входите в свой компьютер, смартфон или другое устройство напрямую.

Процесс аутентификации - это больше, чем просто сравнение двух строк (введённого и сохранённого паролей). Система определяет, какой учётной записи принадлежит введёной логин, проверяет введённый пароль и производит процесс авторизации, создаёт сеанс и выдаёт процессам пользователя маркер доступа. Разберём этот путь на примере локальной учётной записи в современных версиях Windows.

Что означает «локальная»
Локальная учётная запись существует на конкретном компьютере: сведения о ней и её членстве в локальных группах находятся в базе Security Accounts Manager (SAM). Например, PC-01\anna — учётная запись компьютера PC-01. При входе под этой УЗ - проверка может пройти без подключения к сети.

Полезно различать три события. 
Идентификация - отвечает на вопрос «Кто ты?». То есть проверяется существование логина в существующей базе данных. 
Аутентификация - проверка подлинности. То есть при наличии в базе данных введённой учётной записи - проверяются подтверждающие данные: пароль, PIN, отпечаток и т.д.
Авторизация - отвечает на вопрос «Что тебе разрешено?». То есть определяет, разрешён ли данный тип входа и какие действия будут доступны после него.

Путь от экрана входа до рабочего стола
1. Вводи логина (или выбор пользователя на экране входа) и ввод учётных данных (например, пароль).

2. После того как пользователь ввёл пароль на экране входа, специальный компонент Windows, который отвечает за сбор учетных данных (Credential Provider), получает эти введённые значения и упаковывает их для дальнейшей проверки. Дальше через Winlogon запрос уходит в LSA внутри LSASS; LSA выбирает пакет аутентификации, при обычном локальном входе по паролю существенную роль играет MSV1_0. 
Там и начинается уже непосредственная проверка учетных данных.

3. Проверяется локальная запись и пароль. MSV1_0 обращается к SAM. Windows не хранит пароль в виде открытого текста: для проверки используется одностороннее производное от пароля, обычно называемое NT-хешем. Система вычисляет соответствующее значение из введённого пароля и сверяет его с локально сохранённым значением. 

4. Проверяются условия входа (авторизация). Система учитывает состояние записи и политики: например, блокировку учётной записи и право на интерактивный вход. Политики «Разрешить локальный вход» и «Запретить локальный вход» относятся именно к типу входа; запрет имеет приоритет над разрешением. Поэтому верные учётные данные ещё не гарантируют успешный вход.

5. Создаются сеанс и маркер доступа. 
После успешной проверки пакет аутентификации создаёт сеанс входа с собственным идентификатором. LSA формирует маркер доступа (access token), в который входят идентификатор пользователя SID, идентификаторы его групп и привилегии. 
Этот маркер получает пользовательский процесс, а запущенные от него приложения работают в соответствующем контексте безопасности. Загрузка профиля и запуск оболочки превращают успешную проверку в привычный рабочий стол.

6. Права проверяются при работе. Когда программа открывает файл или обращается к защищённому объекту, Windows сопоставляет её маркер с правилами доступа к объекту. Пароль на этом шаге повторно с файлом не сравнивают: система использует уже созданный контекст пользователя. Если Анне разрешён вход в Windows, но у её SID и групп нет права читать папку бухгалтерии, попытка открыть её завершится отказом.

Пример 1. Обычный вход за компьютером

На ноутбуке PC-01 создана локальная запись anna. Анна выбирает её на экране входа и вводит пароль. Logon UI передаёт данные через Winlogon в LSA; MSV1_0 сверяет сведения с SAM этого ноутбука. После проверки условий входа Windows создаёт сеанс и маркер, загружает профиль и показывает рабочий стол. Если Wi-Fi отключён, сама проверка этой локальной записи по-прежнему может пройти: её источник находится на PC-01. Это не означает автоматического доступа к сетевым ресурсам. [1–3, 6]

Пример 2. Пароль верный, но доступ запрещён

Предположим, локальная запись operator существует и пароль введён правильно, однако политика компьютера запрещает этой записи интерактивный вход. Проверка личности и разрешение войти — разные условия; пользователь не получит рабочий стол. Другой вариант: Анна успешно вошла, но не может открыть служебный файл из-за его списка разрешений. В первом случае ограничен вход, во втором — доступ к конкретному ресурсу. [5, 7]

Где здесь NTLM

В учебных материалах термин «NTLM» часто встречается рядом с локальным входом, потому что пакет MSV1_0 участвует и в локальной проверке пароля, и в сценариях аутентификации NTLM. Но NT-хеш, MSV1_0 и сетевой протокол NTLM не обозначают одно и то же. При описанном выше входе с клавиатуры пароль проверяют по локальным данным SAM; трёхсторонний сетевой обмен «согласование → вызов → ответ» между двумя компьютерами для этого не требуется. NTLM как протокол относится к проверке по схеме challenge-response, когда участники устанавливают личность для сетевого доступа. [3, 4, 8]

Пример 3. Доступ к общей папке. Анна с другого компьютера открывает \\PC-01\Shared и предъявляет данные локальной записи PC-01\anna. Если для соединения используется NTLM, сервер выдаёт непредсказуемый вызов (challenge), клиент вычисляет ответ с использованием производного от пароля, а сервер проверяет его по данным своей локальной записи. Пароль в открытом виде по этому протоколу не передаётся. После удачной сетевой аутентификации сервер всё равно проверит, разрешено ли Анне подключаться по сети и читать именно эту папку. Здесь задействована локальная учётная запись целевого компьютера, хотя сам вход относится к сетевому типу. [1, 8, 9]

Если вместо локальной записи предъявлены доменные данные, источник проверки может быть контроллером домена, а протокол и маршрут проверки будут зависеть от сценария. Поэтому фраза «пользователь вошёл в Windows с помощью NTLM» без указания типа входа и места хранения учётной записи слишком неоднозначна.

Что меняется для локального администратора

При включённом контроле учётных записей (UAC) членство в группе «Администраторы» не означает, что каждое приложение сразу запускается с полными административными правами. Для администратора Windows создаёт обычный и административный маркеры; оболочка и обычные программы используют первый. Когда действие требует повышения, UAC запрашивает согласие или учётные данные согласно настройкам. Это происходит после входа и меняет права процесса, а не результат сверки пароля с SAM. [10]

Как увидеть результат проверки

При включённом аудите входа журнал Безопасность на компьютере, куда входят, содержит событие 4624 для успешного входа и 4625 для неудачного. Поле «Тип входа» помогает отличить вход у клавиатуры (2, Interactive) от доступа к общему ресурсу по сети (3, Network) и входа по удалённому рабочему столу (10, RemoteInteractive). Для неудачной попытки следует смотреть также код причины, а не делать вывод только по номеру события. Событие сетевого входа ищут прежде всего на компьютере, который предоставляет ресурс. [9]

Итог

Локальная аутентификация с паролем — это цепочка: экран входа → Winlogon и поставщик учётных данных → LSA/LSASS → MSV1_0 → проверка в SAM → проверка условий входа → сеанс и маркер доступа → доступ к объектам по разрешениям. Понимание каждого звена помогает объяснить, почему правильный пароль не всегда открывает рабочий стол, почему вход без сети возможен для локальной записи и почему доступ к сетевой папке требует отдельной проверки.
