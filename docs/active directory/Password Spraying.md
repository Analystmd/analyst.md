# Password Spraying

> **Password Spraying** - атака, при которой злоумышленник пытается аутентифицироваться сразу под множеством учётных записей, используя один и тот же пароль.

В MITRE ATT&CK это `T1110.003 — Password Spraying`, тактика `Credential Access`

---

## Особенности атаки

Использование данной атаки, позволяет в том числе не достигать **Account Lockout Threshold (порог блокировки учётной записи)** для конкретного пользователя.

Windows считает неудачные попытки отдельно для каждой учётной записи, а параметр `Reset account lockout counter after` определяет, через сколько времени счётчик неудачных входов сбрасывается.

Поэтому атакующий может делать мало попыток на пользователя и растягивать spray по времени.

### Например:

```text
Account lockout threshold = 10
Reset account lockout counter after = 15 min
```

Microsoft в актуальных рекомендациях действительно приводит 10 неудачных попыток как рекомендуемый baseline для threshold, но эти значения можно менять.

То есть в данном случае учётная запись будет заблокирована после достижения 10 неудачных попыток входа, если до этого счётчик не успел сброситься. При `Reset account lockout counter after = 15 min` счётчик неудачных попыток сбрасывается после указанного периода.

А если у злоумышленника есть список из десятков/сотен имён пользователей - то он может держать количество ошибок ниже `Account lockout threshold` и выдерживать интервал, достаточный для сброса счётчика.

# Какие события смотреть:

## 4771 — Kerberos pre-authentication failed

При стандартной парольной Kerberos-аутентификации клиент доказывает знание ключа пользователя через pre-authentication. Если пароль неправильный, KDC не может корректно проверить pre-authentication и для этого типичен:

```text
Event ID:     4771
Failure Code: 0x18
```

```text
0x18 = KDC_ERR_PREAUTH_FAILED
```

### Почему 4625 может не быть?

Потому что атака прекратилась ещё здесь:

```text
получить TGT
    ↓
   FAIL
```

До попытки logon на SERVER01, WS01, FILE01 дело не дошло. Это одна из причин, почему искать Password Spraying только по `4625` недостаточно. `4771` фиксирует именно проблему выдачи Kerberos TGT на KDC

---

## 4776 — NTLM

Если используется NTLM, Domain Controller проверяет credentials.

У 4776 есть ограничение для расследования:

Он содержит:

```text
TargetUserName
Source Workstation
Status
```

но не содержит `destination computer`. Microsoft приводит пример: если CLIENT-1 аутентифицируется на SERVER-1, в 4776 будет виден CLIENT-1, но информация о SERVER-1 в событии отсутствует.

И вот здесь очень полезен `4625`.

---

## 4625 - неудачный logon на целевой системе

4625 принципиально отличается от двух предыдущих.

Это не:

> DC проверил Kerberos.

И не:

> DC проверил NTLM credentials.

Это:

> На этой Windows-системе была предпринята попытка logon, и она завершилась неудачей.

4625 создаётся на компьютере, где была сделана попытка входа. Это может быть DC, member server или workstation

---

# Связка 4625 + 4776

Получаем два события об одной логической попытке:

### FILESERVER01:

```text
4625
TargetUser = user01
SourceIP = 10.10.10.50
LogonType = 3
Status/SubStatus = bad password
```

### DC01:

```text
4776
TargetUser = user01
Workstation = ATTACKER-PC
Status = bad password
```

Они не дублируют друг друга.

**4776 говорит:**

> Domain Controller отклонил NTLM credentials.

**4625 говорит:**

> На FILESERVER01 не удался network logon.

# Как защититься?

### Для пользователей:

создавайте длинные, уникальные пароли (лучше парольные фразы) и не повторяйте их в разных сервисах. Обязательно включайте многофакторную аутентификацию (MFA) — это серьёзный барьер даже если пароль украдут.

### Для организаций:

внедрите чёткую политику паролей (проверяйте новые пароли на популярность), используйте менеджеры паролей для хранения доступов, а также настройте системы мониторинга, чтобы фиксировать массовые попытки входа из нетипичных мест или в необычное время.

---

# Как детектировать?

Смотрим на большое количество `4771/4776/4625` с кодами/статусами/сабкодами, обозначающими неудачную попытку аутентификации:

```text
4771 / 0x18
4776 / 0xC000006A
4625 / 0xC000006A
```

При этом для Password Spraying важен не просто большой объём ошибок, а **большое количество различных TargetUser с одного источника за определённый промежуток времени и небольшое количество попыток на каждую отдельную учётную запись.**

Параллельно смотрим, появляются ли успешные попытки аутентификации с того же источника во время или вскоре после серии неудачных попыток.

### Дополнительно сравниваем:

```text
SourceIP / Workstation
TargetUser
DestinationHost
LogonType
AuthenticationPackage
WorkstationName
```

> Отдельно стоит учитывать low-and-slow Password Spraying, когда атакующий растягивает попытки во времени, поэтому одного короткого временного окна может быть недостаточно.
